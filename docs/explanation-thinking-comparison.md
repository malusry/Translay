# 详细解释：思考开关对比

结论：现用提示词不变时，开启思考在本轮困难合成样例上有明显收益，但仍不满足稳定通过的标准。没有修改应用设置、提示词、翻译流程或界面。

## 固定实验

- 模型：已配置的 deepseek-v4-flash，使用同一官方 DeepSeek 接口。
- 只改变 `thinking.type`：disabled / enabled；与应用现有开关的请求参数一致。开启组 20 次均返回了思考字段，关闭组均未返回；没有保留或审阅思考正文。
- 同一生产提示词、同一 user 消息结构、同一输入，默认 temperature，不额外指定 response_format 或 token 上限。
- 10 例，每例每种模式重复 2 次，共 40 次；种子 915 打乱请求顺序，最多并发 2 个，60 秒超时，无重试，无中途提示词调整。
- 8 例来自此前困难样例，另有 2 例本次首次加入：观察结果的必要条件、上下文明确根号范围而译文错误。新例未用于调整提示词。
- 先按 trialId 和 caseId 审阅最终答案，不展示模式和耗时，再揭示模式统计。这是助手人工判断，不是独立评审员评审，也不是完全盲法实验。

## 结果

| 指标 | 关闭思考 | 开启思考 |
|---|---:|---:|
| 完全通过 | 5 / 20 | 13 / 20 |
| 待精简或措辞修正 | 2 / 20 | 3 / 20 |
| 未通过 | 13 / 20 | 4 / 20 |
| 严格 JSON 字段格式通过 | 20 / 20 | 20 / 20 |
| 两次均完全通过的样例 | 1 / 10 | 4 / 10 |
| 请求耗时中位数 | 0.93 秒 | 5.17 秒 |
| 请求耗时均值 | 1.00 秒 | 7.82 秒 |
| 最慢请求 | 1.58 秒 | 33.55 秒 |

“完全通过”同时要求语义正确与表达克制；“待精简”表示主要含义保留，但有重复或措辞问题；“未通过”包括错误推断、无依据补充，以及漏掉预定要求中的重要歧义或译文冲突。逐例标准在请求前固定，见 JSON 中 cases.rubric。

应用实际 MathText 分词与渲染函数识别到 32 个公式片段，均可渲染，没有检测到重复转义命令。能渲染不等于公式含义正确，也不代表所有纯文本数学都已排版。

## 改善与剩余问题

开启组在充分条件、否定量词、置信区间前提和观察范围内的必要条件方面更可靠。两个新样例的 4 次请求中，关闭组为 1 通过、3 未通过；开启组为 3 通过、1 待精简。

开启组仍存在：
- 缺失指代：两次中一次漏掉必要提示。
- 分数缩放：两次中一次擅自加入“注意力分数”。
- 残差缩放：两次中一次声称缩放后不再受尺度参数影响。
- 根号范围未知：两次均未完全通过，一次正文确定范围、提示却说不确定；另一次重复讨论范围。

这些问题说明思考能力有帮助，但不能单独保证证据边界与精简要求。

## 使用建议与限制

下一步可评估“详细解释单独开启思考”，保持快速翻译原有模式。当前思考开关被翻译和解释共用，本次不直接开启全局设置，避免把延迟带入所有翻译请求。这只是下一步建议，并未实现独立开关或自动校对。

每例仅重复两次，且大部分是已知困难样例；比例不能当作日常使用成功率，两个新例也不足以证明泛化能力。耗时包括网络与服务等待，并非纯推理耗时；并发、缓存和服务波动会影响结果。本轮为直接 API 验收，不覆盖原生划词、IPC 或真实论文解释体验。
